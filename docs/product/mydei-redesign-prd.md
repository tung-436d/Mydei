## 1. 文档目的与约束

本文档用于把现有“黄金蜜饼”静态多页站，渐进式完善为高完成度的“万敌角色专题站”。方案优先复用当前有效内容和交互，不默认推倒重做。

内容约束：

- 未经核验的角色属性、技能描述、倍率、剧情、语录、养成结论均不得作为确定事实发布。
- 所有待核验字段统一显示或记录为“待确认”，禁止使用模型推测补齐。
- 页面必须明确区分“官方信息”“玩法建议”“站点原创描述”。
- 不下载或引入未经确认授权的游戏素材；现有素材也应补做来源与使用权限审计。
- 本站不得在名称、视觉或文案上暗示为《崩坏：星穹铁道》或其权利方的官方网站。

### 2.4 当前问题

#### 内容

1. 主体仍是个人粉丝页/“黄金蜜饼”站，缺少万敌的基础资料、技能、行迹、星魂、装备、配队、机制循环等用户核心任务。
2. “图书馆藏”存在大量长文本，但缺少来源、版本、是否官方原文/摘录/原创整理的标记；可信度和版权边界无法判断。
3. “纷争剧作”为纯占位页；首页第三张卡片也是“未完待续”，有效内容入口不足。
4. 角色名称同时使用“万敌”“Mydeimos”“迈德漠斯”“小敌”，未解释称谓关系，也没有统一的页面主标题和搜索关键词策略。
5. 联系方式与作者介绍比角色资料更完整，专题目标被稀释。

#### 信息层级

1. 主导航仅“首页 / 关于 / 更新日志”，不能直接到达技能、养成、配队、故事、画廊等高频内容。
2. 封面没有可见站点标题、价值说明或主行动按钮；访客难以判断网站用途。
3. 首页先展示引语，再给出语义含糊的卡片；缺少“快速认识角色 → 理解技能 → 获取养成建议 → 深入故事”的任务路径。
4. 辅助信息（关于作者、更新日志）占据一级入口，核心信息没有章节导航、面包屑或深链接。
5. 长文只有逐项展开，没有内容摘要、目录、筛选、阅读进度或返回上下文的路径。

#### 视觉

1. 当前样式更接近通用个人主页：系统无衬线字体、白色圆角卡片、常规阴影较多，古典英雄史诗感不足。
2. 深红棕被同时用作正文、标题、强调和页脚，色彩角色没有分工，缺少金属、石材、黑曜石和火焰意象形成的层次。
3. 角色主视觉在桌面端由 200×200 头像放大到约 400×400，细节有限；在移动端又缩成极小图像，视觉重心不稳定。
4. 页面之间完成度差异大：封面沉浸、首页卡片化、长文列表化、占位页无样式，缺乏统一设计语言。
5. 大图 `img_mydei.jpg` 约 4 MB，现有多张 PNG 超过 1 MB；未见响应式图片、现代格式或加载策略。

#### 交互

1. 交互基本只有页面跳转、悬停和折叠，不能支持技能对比、章节定位、构筑切换、配队理解等专题任务。
2. 顶部 `header` 内元素使用浮动，实测首页 header 计算高度为 0；粘性导航的占位和锚点偏移可能不可靠。
3. 导航缺少移动端展开/收起模式，也没有明确的当前章节状态。
4. 卡片悬停上移对鼠标有效，但触屏没有对应反馈；多个页面的交互状态和焦点样式不一致。
5. 长内容没有“展开全部/收起全部”、复制章节链接或返回顶部等辅助能力。

#### 移动端

1. 390×844 实测时首屏仍尝试横向容纳文案与图片，角色头像被压缩到约 30 px 级视觉尺寸，失去首屏主角地位。
2. 导航三项始终横排并右浮；当前内容尚能容纳，但新增专题导航后必然拥挤。
3. 仅有少量针对 `.navbar/.nav-links` 的断点规则，而实际 HTML 使用 `.list/.navlist`，多项响应式声明未作用于现有结构。
4. 页面纵向节奏偏长，三张大卡片连续堆叠；缺少移动端的章节捷径和紧凑信息摘要。
5. 长文阅读缺少适合窄屏的行长、段落间距、目录与展开控制规范。

#### 可访问性

1. 全部页面均无 `<main>`；导航列表没有 `<nav>` 语义，且没有“跳到主要内容”链接。
2. 封面无 H1；页面虽有 H1，但卡片直接使用 H3，标题层级存在跳级。
3. 主要链接多数只定义 hover，未统一定义清晰的键盘 focus；卡片的 focus 样式是局部例外。
4. 当前深棕/暖白组合需正式做对比度审计；页脚灰字、未来金色文字尤其需要验证 WCAG AA。
5. 图片替代文本如“小敌照片”偏口语且不能说明图像功能；背景图没有文本等价内容。
6. 展开内容、章节切换和未来画廊尚无键盘、屏幕阅读器、焦点回收及状态播报规范。

#### SEO 与工程基础

1. 所有页面均无 meta description、canonical、Open Graph/Twitter Card 或结构化数据。
2. 标题以“黄金蜜饼”为主，无法覆盖“万敌 / Mydei / Mydeimos / 崩坏：星穹铁道”等合理搜索意图。
3. 路由大小写混用且目录层级表达内容组织，不利于稳定 URL 和迁移。
4. 公共页头、页脚和大量 CSS 重复，后续改版容易出现跨页不一致。
5. 无 README、依赖声明、内容 schema、自动化检查和性能基线，架构与维护约束尚未形成。

## 3. 产品定位

### 3.1 一句话定位

一个以万敌为唯一主角、兼顾角色设定、战斗理解、养成决策与视觉欣赏的高完成度中文粉丝专题站。

### 3.2 核心价值

- **快速认识**：在首屏和基础资料区回答“万敌是谁”。
- **准确理解**：以有来源、可追溯的技能与机制信息回答“角色怎么运作”。
- **辅助决策**：用明确标记为玩法建议的装备、词条、配队与循环建议回答“如何培养和使用”。
- **沉浸浏览**：用克制而有史诗感的视觉和故事组织回答“为什么喜欢这个角色”。

### 3.3 非目标

- 不建设全角色数据库、抽卡模拟器或完整游戏百科。
- 不追求复刻游戏客户端或官方站视觉。
- MVP 不做账号、评论、投稿、社区、实时榜单或自动抓取第三方数据。
- 不以未经验证的数值计算器作为核心卖点。

## 4. 产品目标与衡量方式

| 目标 | 用户结果 | MVP 衡量标准 |
| --- | --- | --- |
| 建立明确专题心智 | 进入 5 秒内知道这是万敌角色专题站 | 首屏同时出现角色名、定位短句、资料/玩法两个主入口和非官网简短标识 |
| 覆盖核心信息任务 | 用户可完成认识、理解技能、查看养成和配队 | P0 模块全部上线且无无效占位入口 |
| 建立内容信任 | 用户能识别信息来源与内容性质 | 100% 事实型字段含状态标签；100% 官方信息含来源记录；待核验数据不以确定值展示 |
| 提升阅读与导航效率 | 任一核心章节可直接到达并可分享 | 章节导航和稳定锚点覆盖全部 P0 模块；桌面/移动均可用 |
| 保证体验底线 | 正文可读、移动端不退化、键盘可操作 | 满足第 14 节性能与可访问性指标，通过第 17 节验收 |

如上线后具备匿名统计并获得合规同意，可观察：首屏到核心章节点击率、各模块到达率、构筑/队伍卡展开率、章节深链访问量。MVP 不以采集个人信息为前提。

## 5. 目标用户

### 5.1 核心人群

1. **万敌爱好者**：希望获得角色氛围、设定、语录、故事与高质量视觉内容，并愿意反复浏览。
2. **角色信息查询者**：希望快速确认属性、命途、阵营、技能、行迹和星魂，不想在长文中查找。
3. **培养与战斗玩家**：希望理解机制、操作循环、光锥/遗器/词条/配队的选择依据。
4. **视觉浏览访客**：可能只认识角色外观，希望轻量欣赏图片并进一步了解角色。

### 5.2 关键场景

- 手机端从分享链接进入，1 分钟内判断角色定位和玩法特点。
- 桌面端游玩时并排打开，快速查技能、配装或战斗循环。
- 粉丝深度阅读角色故事与语录，并能确认来源和剧透级别。
- 通过搜索引擎进入具体技能/配队锚点，而非必须从封面逐级进入。

## 6. 产品与内容原则

1. **角色优先**：每个首屏和一级导航都服务于角色认知，不让站主信息抢占主任务。
2. **先结论，后细节**：摘要在前，可展开原文、机制解释和依据。
3. **事实与观点分层**：官方事实、玩法建议、原创氛围文案使用一致且可感知的标签系统。
4. **渐进式增强**：核心内容在无 JavaScript 时仍可阅读；动效、标签切换和画廊是增强，不是访问门槛。
5. **克制的史诗感**：用构图、材质、排版和留白建立气质；发光、粒子、火焰、视差只用于少数关键节点。
6. **移动优先但不牺牲桌面沉浸**：移动端先保证角色可见、正文清晰、操作紧凑；桌面端再扩展构图与并列信息。

## 7. 内容可信度与治理

### 7.1 内容类型标签

| 标签 | 定义 | 展示与录入规则 |
| --- | --- | --- |
| 官方信息 | 可由游戏内文本、官方角色介绍、官方公告/演示等一手来源核验 | 必须记录来源标题、来源位置/URL、适用版本、核验日期；引用须控制长度并遵守版权 |
| 玩法建议 | 由站点编辑或已注明作者基于机制提出的培养/战斗建议 | 必须写明适用前提、版本、推荐理由；避免“唯一最优”等无条件措辞 |
| 站点原创描述 | 为氛围、导览或总结而创作的非官方表达 | 必须显式标记，不使用仿官方口吻制造误认 |
| 待确认 | 当前无法从可信来源确认，或版本/翻译存在冲突 | 不显示猜测值；可显示字段名与“待确认”，后台/内容文件记录待办原因 |

### 7.2 来源优先级

1. 游戏内当前版本可见文本或官方角色资料。
2. 游戏官方网站、官方社交账号、官方视频/直播内容。
3. 可信数据库或攻略作者，仅用于交叉核对或玩法建议，不冒充官方来源。
4. 玩家讨论只可作为“社区观点”线索，未经核验不得转为事实。

### 7.3 发布门槛

- 数值字段至少完成一次人工对照；技能倍率必须注明等级/版本/口径，否则保持“待确认”。
- 剧情与语录必须有出处和剧透分级；涉及长篇官方文本时优先摘要并链接来源，不整段搬运。
- 每条玩法建议必须有作者/编辑、最后复核日期、适用版本和理由。
- 内容冲突时展示“存在版本差异/待确认”，不静默选择一个答案。
- 每次游戏版本更新后，对带版本字段的内容执行复核；未复核内容显示“尚未适配当前版本”。

## 8. 信息架构

### 8.1 推荐站点结构

```text
万敌角色专题站
├─ 专题首页（单页主叙事，可深链接）
│  ├─ 首屏 / 角色概览
│  ├─ 基础资料与角色设定
│  ├─ 技能
│  ├─ 行迹与星魂
│  ├─ 养成建议（光锥、遗器、词条）
│  ├─ 配队推荐
│  ├─ 机制与操作循环
│  ├─ 故事、语录与时间线
│  ├─ 图片画廊
│  └─ 来源、免责声明与更新信息
├─ 来源与勘误（可独立辅助页）
├─ 更新日志（复用现有内容并降为辅助入口）
└─ 关于本站（作者、联系、版权/非官网说明）
```

### 8.2 导航建议

- 一级常驻导航控制在 5 项：`概览 / 技能 / 养成 / 配队 / 故事`。
- `行迹与星魂`并入技能章节；`机制循环`在技能与配队中均提供上下文入口。
- `画廊 / 来源 / 关于 / 更新日志`置于“更多”或页脚，避免挤占核心路径。
- 每个核心模块拥有稳定、可读锚点；示例仅表达语义：`#skills`、`#build`、`#teams`、`#story`。
- 桌面端提供粘性章节导航与当前章节状态；移动端使用紧凑顶部栏 + 可展开目录，打开后焦点受控并可关闭。

### 8.3 推荐浏览路径

- 新访客：首屏 → 角色概览 → 技能机制 → 养成/配队。
- 查询者：搜索/分享深链 → 对应章节 → 相关建议 → 来源。
- 粉丝：首屏 → 角色设定 → 故事/语录 → 画廊。

## 10. 模块详细需求

### 10.1 首屏与角色概览（P0）

- H1 使用“万敌”，英文/其他称谓作为副标题或别名，不让 `Mydeimos` 成为唯一可见名称。
- 一屏内回答：角色是谁、本站提供什么、可去哪里。
- 桌面端角色视觉占首屏显著区域但不遮挡文本；移动端改为纵向构图，角色图不得被压缩为装饰性小点。
- 主 CTA：“查看角色资料”；次 CTA：“查看玩法建议”。均链接到同页稳定锚点。
- 首屏底部以简短文字声明“非官方网站；相关权利归原权利方所有”，完整声明放页尾。
- 粒子/火星/视差只允许作为非必要装饰；默认低密度，不影响文字，不响应时不阻塞内容。

### 10.2 角色简介与基础资料（P0）

- 简介摘要与资料卡并列或相邻，优先提供可扫描关键词。
- 资料字段包括但不限于：中文名、其他称谓、属性、命途、阵营/所属、稀有度、首次可用版本、角色定位。
- 每组资料显示内容类型标签；字段级待确认状态不能被全局“官方信息”标签掩盖。
- 允许将“黄金蜜饼”作为经核验后的相关轶事/彩蛋卡片，但不占据基础资料主位。

### 10.3 技能（P0）

- 分类固定为：普攻、战技、终结技、天赋、秘技；若角色实际机制存在额外形态，须由内容 schema 支持但不得先行编造。
- 桌面可用标签页或纵向章节；移动端优先可滚动的短摘要 + 原生展开详情，不把全部长文本塞进横向标签。
- 每项至少包含：名称、类型、官方效果摘要/文本、机制关键词、站点解读、来源、适用版本。
- 倍率按技能等级/形态结构化存储；未核验时整块标“待确认”，不得展示占位数字。
- 标签切换支持键盘；深链接可定位到具体技能，刷新后状态保持。

### 10.4 行迹与星魂（P0）

- 行迹按能力节点组织，关键行迹提供“为什么重要”的玩法建议。
- 星魂按序号 1–6 展示，默认先显示简短影响；完整描述可展开。
- 不用仅依赖金/灰颜色表达“推荐/非推荐”，同时给文字或图标含义。
- 站点解读不得改写成类似官方技能文本的语气。

### 10.5 养成建议（P0）

- 光锥、遗器/位面饰品、主词条、副词条分组展示。
- 每项建议包括：名称、推荐层级、适用场景、推荐理由、限制/替代方案、最后复核版本。
- 推荐层级使用“优先 / 可选 / 过渡”或同类中性表达；不使用无法证实的百分比差距。
- 词条建议必须注明前提（队伍、速度阈值、装备组合等）；无法确认时标“待确认”。
- 内容层支持“一眼结论”和“展开依据”，兼顾快速查询与深读。

### 10.6 配队推荐（P0）

- 队伍以职责槽位而非仅固定角色列表表达，例如：核心 / 生存 / 增益 / 副输出；具体命名待机制核验。
- 每套包含：队伍定位、成员与职责、替代位、适用场景、基本循环、优点、限制。
- 若使用角色头像，必须有可见角色名和合适的 alt，不能依赖图像识别。
- 同一建议注明版本；角色或机制变动后可被标记为“待复核”。

### 10.7 机制与操作循环（P0）

- 用 3–6 步的流程说明“进入战斗 → 建立状态/资源 → 关键动作 → 终结技时机 → 循环/异常分支”。具体步骤须等待机制核验。
- 复杂机制可用静态流程图辅助，必须同时提供等价文本。
- 增设“常见误区”与“何时偏离标准循环”，避免让用户把建议理解为唯一操作。
- 不在 MVP 提供会被误认成精确模拟的动态伤害计算结果。

### 10.8 故事、语录与时间线（P1）

- 默认显示无重大剧透摘要；带剧透内容需要明确开关，用户选择在当前会话内保持。
- 时间线只使用可核验事件；无法确认时间顺序时用“顺序待确认”，不强行排序。
- 现有图书馆藏内容先做来源/版权审计，再决定保留原文、改写摘要或仅做外链索引。
- 长文支持章节目录、单项展开、展开全部/收起全部和章节深链。

### 10.9 图片画廊（P1，授权门槛）

- 每张图片必须有：标题/说明、来源、作者/权利方（如适用）、授权状态、替代文本、尺寸与裁切安全区。
- 缩略图懒加载；首屏主视觉不得与画廊抢占同一高优先级资源。
- 灯箱支持键盘打开/关闭、左右切换、焦点圈定与回收；触屏支持按钮，不强制依赖滑动手势。
- 不为填满画廊而抓取或下载未经授权素材。

### 10.10 来源与声明（P0）

- 页尾固定出现非官方网站声明，并链接至完整来源页。
- 来源可按“角色资料 / 技能 / 玩法建议 / 故事与语录 / 图片”分组。
- 每条来源记录：标题、发布者、来源类型、URL/游戏内位置、适用版本、访问/核验日期、覆盖字段。
- 提供勘误方式，但公开邮箱、QQ、社交链接是否继续展示由站主确认。

## 11. 关键交互说明

### 11.1 章节导航与深链接

- 页面滚动时更新当前章节；更新不得造成历史记录刷屏或屏幕阅读器持续播报。
- 点击章节后将标题滚动至粘性页头下方，并把焦点移至章节标题。
- 直接访问锚点或刷新时必须定位正确；禁用 JavaScript 时锚点仍工作。
- 桌面端当前章节明显；移动端目录按钮显示当前章节名或选中状态。

### 11.2 折叠、标签与内容密度

- 优先使用原生 `details/summary` 或等价可访问组件。
- 默认展示摘要，不把关键结论藏在折叠中；倍率、来源、长解释可展开。
- “展开全部”仅用于同一小节，避免一次展开整页造成性能和认知负担。
- 标签页必须具备正确 tab/tabpanel 语义、方向键切换和可分享状态；若实现成本过高，使用纵向章节。

### 11.3 构筑与配队卡

- 卡片点击/展开后显示依据与替代项；整卡可点时不得嵌套冲突交互。
- 筛选或切换不应清空用户滚动位置；状态变化有可感知标题，不仅靠动画。
- 不用悬停才能看到关键信息；触屏、键盘和鼠标获得等价内容。

### 11.4 剧透控制

- 剧透开关默认关闭；开关有明确范围（本节/全站）。
- 遮罩内容对辅助技术不能默认直接朗读；展开后将焦点合理移动到内容标题。
- 不通过永久账号保存；如使用本地偏好，需在隐私说明中写明且提供重置。

### 11.5 动效

- 动效服务于入场层级、章节切换和机制说明，不装饰每张卡片。
- 普通过渡建议 150–300 ms；大幅视差和持续粒子不得遮挡或拖慢首屏。
- `prefers-reduced-motion: reduce` 下关闭自动移动、视差、粒子和非必要平滑滚动。
- 页面不可因动画前状态而短暂隐藏核心正文。

## 12. 视觉体验方向

### 12.1 设计关键词

`古典英雄`、`孤王与守护`、`石刻史诗`、`炽热金属`、`深空余烬`、`庄重而非奢靡`。

### 12.2 色彩角色（方向值，设计阶段需做对比度验证）

| 角色 | 建议方向 | 用途 |
| --- | --- | --- |
| 黑曜石 | 近黑 `#12100F` 一类 | 深色章节、页头、沉浸背景 |
| 深红 | `#5A1717` 一类 | 关键分区、状态、强调，不用于大段正文 |
| 古金 | `#C6A15B` 一类 | 边线、图标、关键标题和少量高光 |
| 暖白 | `#F4EBDD` 一类 | 正文底色、深色背景上的主文本 |
| 石灰/烟灰 | 中性灰棕 | 次级文本、分隔和石材层次 |

金色不作为小字号正文色；所有最终色值以 WCAG 2.2 AA 实测为准。

### 12.3 材质与构图

- 用细边线、压印纹理、石材颗粒、金属铭牌和大面积暗部塑造材质，不依赖厚重发光。
- 首屏构图强调角色轮廓与标题，正文区域回归稳定的暖白/深色高对比阅读面。
- 火焰和星穹意象可用于章节分隔或首屏局部，不铺满全站。
- 卡片减少“通用 SaaS 白卡”感，改用更克制的平面层、边框和材质差异。
- 装饰纹理应压缩、可关闭/可降级，不降低正文对比度。

### 12.4 排版

- 展示标题可采用具古典气质且具合法授权的中文展示字体；正文优先高可读中文字体栈。
- 正文桌面端建议每行约 45–75 个中文字符的可读宽度；移动端使用完整可用宽度与稳定边距。
- 中英文名、称谓、属性标签形成明确层级；避免纯大写英文承担主识别。
- 字体文件若自托管，必须确认授权并做子集化；字体失败时不得破坏层级。

### 12.5 差异化边界

- 不复制官方站的导航结构、动效编排、图形组件或完整视觉资产组合。
- 以“角色档案 + 英雄史诗章节”的编辑设计为独立概念，而非仿游戏 UI。
- 官方商标只用于合理指称与免责声明，不设计成疑似官方徽章。

## 13. 桌面端与移动端需求

### 13.1 响应区间

具体断点由工程依据内容决定，不以设备型号硬编码。验收至少覆盖 360、390、768、1024、1280、1440 CSS px 宽度。

### 13.2 桌面端

- 首屏允许文字与角色视觉双栏；正文最大内容宽度受控，背景可延伸全宽。
- 技能/构筑可采用主内容 + 辅助目录双栏，但关键内容不能只在侧栏。
- 粘性导航不得遮挡标题，缩放至 200% 时仍可访问全部项目。
- 画廊允许多列；技能与队伍卡可以并列比较，但不得造成过小正文。

### 13.3 移动端

- 首屏改为单列或经过验证的叠层构图：角色主体清晰可见，H1、简介和 CTA 不互相遮挡。
- 一级导航折叠为可访问菜单；目录打开后可关闭、可返回触发按钮，背景滚动策略一致。
- 核心触控目标至少 44×44 CSS px，目标间保留足够间距。
- 复杂表格改为卡片/定义列表或允许有提示的局部横向滚动；页面本身禁止横向溢出。
- 技能、行迹、星魂默认摘要化，减少一屏内的信息密度；关键结论不依赖 hover。
- 长文正文最小 16 CSS px，合理行高；页面缩放、系统大字体下不截断。
- 不因节省空间将角色主视觉压缩为无法识别的缩略图。

### 13.4 方向与设备能力

- 竖屏/横屏切换不丢失展开、标签或剧透状态。
- 低性能设备和节省流量场景下，无粒子/视差仍有完整信息与稳定构图。
- 安全区内边距适配刘海/底部手势区（如采用全屏或固定控件）。

- 分等级倍率、技能等级上限和特殊形态映射。
- 行迹：节点、类型、解锁条件、官方描述、玩法解读、材料（如纳入）。
- 星魂 1–6：名称、官方描述、机制影响、玩法解读。

**当前状态：所有技能名、效果、倍率、行迹和星魂数据待确认。**

### 14.4 养成与队伍数据

- 光锥：名称、层级、适用条件、理由、限制、来源/版本。
- 遗器/位面饰品：套装、件数、主词条、副词条、阈值前提、替代项。
- 队伍：名称、场景、4 个职责槽、具体成员、替代位、循环、优缺点。
- 机制循环：步骤、前置状态、分支、误区、关联技能。

**当前状态：全部推荐结论和排名待玩法负责人基于已核验机制编写。**

### 14.5 叙事与媒体数据

- 故事事件：标题、摘要、顺序/时间、参与者、剧透级别、来源。
- 语录：短摘录、说话者、场景、出处、版本、剧透级别。
- 图片：文件、用途、标题、说明、alt、来源、作者/权利方、授权状态、尺寸、焦点/安全裁切。
- 现有图书馆藏条目：逐条登记来源性质、版权处置与是否与万敌直接相关。

### 14.6 来源数据

- 来源 ID、标题、发布者、来源类型、URL 或游戏内路径、发布日期（如有）、访问日期、适用版本、备注。
- 来源与内容字段为多对多关系，以便一次更新识别受影响内容。
- URL 失效时保留来源元数据并标“链接失效/待替换”，不删除核验历史。

## 15. SEO、性能与可访问性要求

### 15.1 SEO

- 每个可索引页面只有一个描述性 H1，并具有唯一 title 与 meta description。
- 专题首页标题需自然包含“万敌”“崩坏：星穹铁道”；别名作为可读文本出现，不堆砌关键词。
- 稳定 canonical、语义化 URL、站点地图、robots 策略和 404 页面由架构方案统一决定。
- 提供 Open Graph 基础字段；分享图只能使用授权确认素材。
- 使用 `Person`/`VideoGame` 等结构化数据前先验证 schema 语义；不得把虚构角色错误声明为现实人物，也不得标为官方网站。
- 核心事实和摘要必须存在于 HTML，不依赖客户端脚本执行后才可被读取。
- 锚点标题可通过搜索或分享直达；URL 迁移必须配置映射，避免现有链接直接失效。

### 15.2 性能

- 目标（真实移动端第 75 百分位）：LCP ≤ 2.5 s、INP ≤ 200 ms、CLS ≤ 0.1。
- 在约定测试环境下，Lighthouse Mobile：Performance ≥ 90、Accessibility ≥ 95、SEO ≥ 95；环境和重复次数须记录。
- 首屏主视觉使用合适尺寸、现代格式与响应式资源；不得继续无条件发送约 4 MB 原图。
- 非首屏画廊/故事图片懒加载；首屏关键图仅预加载实际会使用的单一候选。
- 动效以 transform/opacity 为主并限制并发；持续粒子具备降级和关闭路径。
- 字体子集化、`font-display` 策略与系统回退明确；避免为装饰加载多个大字体。
- 无 JavaScript 时核心文字、资料、来源和链接仍可访问。

### 15.3 可访问性

- 目标遵循 WCAG 2.2 AA。
- 使用 `header/nav/main/section/footer` 等正确地标；每页有跳到主要内容链接。
- 标题顺序不跳级；列表、定义列表、表格按数据语义选择。
- 普通正文对比度 ≥ 4.5:1，大文本 ≥ 3:1；组件边界/焦点等非文本对比度 ≥ 3:1。
- 全部功能可用键盘操作，焦点顺序符合视觉顺序，焦点不被粘性层遮挡，焦点样式全站可见。
- 菜单、标签、灯箱、剧透开关和展开组件提供正确名称、角色、状态与焦点管理。
- 内容不只靠颜色、位置、图标或动画表达；图表提供文本等价内容。
- 信息图片提供有意义 alt；纯装饰图片使用空 alt；背景角色图必须有相邻文本等价信息。
- 支持 200% 页面缩放与 400% reflow；360 CSS px 宽度不出现页面级横向滚动。
- 尊重 `prefers-reduced-motion`；不得自动播放不可暂停的持续动画。
- 中文语种正确；混合英文名时可按需标注语言，避免读屏误读。

## 16. 范围

### 16.1 MVP（P0）

- 专题首页与统一全局页头/页脚。
- 首屏角色展示、角色简介、基础资料。
- 普攻/战技/终结技/天赋/秘技展示。
- 行迹与星魂。
- 光锥、遗器/位面饰品、词条建议。
- 配队推荐。
- 战斗机制与操作循环。
- 来源、内容标签、适用版本、最后更新、勘误入口和非官网声明。
- 桌面与移动响应式、键盘与减少动画支持、基础 SEO 与性能优化。
- 仅使用已确认可用的现有素材；授权未确认不阻塞纯内容/布局版本上线。

MVP 发布条件不是“所有数值都填满”，而是“所有已发布数据均可信”。无法核验的字段应留为待确认、隐藏具体值或暂缓该细项，不得用猜测填充。

### 16.2 后续增强（P1）

- 故事、时间线、语录与剧透控制。
- 经来源/版权审计后的图书馆藏迁移。
- 授权素材画廊与可访问灯箱。
- 更新日志、关于本站和来源页的完善。
- 构筑/队伍轻量筛选、展开全部、复制章节链接。
- 更精细但仍克制的材质、火星、星穹与视差效果。

### 16.3 远期增强（P2）

- 内容规模达到阈值后的全站搜索与多条件过滤。
- 经严格公式、数据与版本治理支持的构筑对比/伤害计算。
- 多语言、离线阅读、版本差异查看。
- 经隐私评审后的匿名行为分析或内容反馈工作流。

## 17. 明确验收标准

### 17.1 内容与定位

- [ ] 进入首页无需滚动即可看到“万敌”、专题价值说明、至少 2 个核心 CTA 和非官方网站简短声明。
- [ ] P0 所有模块可从一级导航或清晰的二级入口到达，不存在“未完待续”式无效核心入口。
- [ ] 100% 已发布事实字段具有“官方信息”或“待确认”等状态；官方信息可追溯到来源记录。
- [ ] 100% 玩法建议显示适用版本、理由和最后复核日期；与官方描述视觉/语义区分。
- [ ] 100% 原创氛围文案标明“站点原创描述”。
- [ ] 不出现未经核验的技能倍率、剧情断言、官方设定或伪造来源。

### 17.2 功能与交互

- [ ] 章节导航覆盖概览、技能、养成、配队、故事/档案入口；当前章节状态正确。
- [ ] 每个 P0 章节具有稳定深链接；直接访问、刷新、前进/后退后仍定位正确。
- [ ] 普攻、战技、终结技、天赋、秘技均有独立可识别入口和来源/状态展示。
- [ ] 行迹与星魂、构筑、队伍、循环的摘要与详情均可在鼠标、触控和键盘下访问。
- [ ] 无 JavaScript 时仍可阅读角色概览、核心资料、技能文本、建议摘要、来源和声明。
- [ ] 页面不存在失效的站内主导航链接或无法退出的弹层。

### 17.3 响应式与视觉

- [ ] 在 360、390、768、1024、1280、1440 px 宽度完成手工检查，无页面级横向滚动、内容遮挡或不可见操作。
- [ ] 移动端首屏角色主视觉可识别，不出现当前约 30 px 级缩略退化；H1、简介、CTA 均无需横向滚动。
- [ ] 44×44 CSS px 触控目标要求覆盖菜单、标签、展开、灯箱和主要 CTA。
- [ ] 正文行长、字号和行高符合第 12/13 节；长文在移动端连续阅读无异常断行。
- [ ] 发光、粒子、火焰和视差不覆盖正文、不成为信息载体，并能在减少动画偏好下关闭。
- [ ] 视觉没有复制官方站的页面结构或标志性组件组合。

### 17.4 可访问性

- [ ] 每页有唯一 H1、`main` 地标、语义导航、跳到主要内容链接和逻辑标题层级。
- [ ] 键盘可完成全站核心任务；焦点始终可见且不被粘性页头遮挡。
- [ ] 菜单、标签、折叠、剧透和灯箱通过屏幕阅读器抽查，名称/状态/焦点回收正确。
- [ ] 所有最终颜色通过 AA 对比度检查；不只靠颜色传达内容类型或推荐等级。
- [ ] 图片替代文本台账完成；装饰图为空 alt，信息图有等价文字。
- [ ] 200% 缩放和 400% reflow 检查通过；减少动画模式无持续非必要运动。

### 17.5 SEO 与性能

- [ ] 所有可索引页面具有唯一 title、description、canonical 和正确 `lang`。
- [ ] 分享预览字段完整，预览图授权状态已确认。
- [ ] 无断裂内部链接，旧 URL 的保留或重定向方案完成并测试。
- [ ] 性能达到第 15.2 节目标；测试报告包含设备/网络配置和至少 3 次结果。
- [ ] 首屏不直接传输未经优化的约 4 MB 背景原图；图片尺寸匹配显示需求且不引起布局偏移。

### 17.6 合规与来源

- [ ] 页脚和完整来源页均有清晰的非官方网站声明及权利归属说明。
- [ ] 所有上线图片都在素材台账中标记来源、权利方与可用状态。
- [ ] 现有长篇馆藏文本已逐条完成来源与版权处置决定，未审计内容不进入公开新版。
- [ ] 对外联系方式经站主确认可继续公开，且与角色内容层级分离。

## 18. 需要架构工程师决定的问题

以下问题需要在技术方案评审中形成 ADR 或等价的可追溯决策：

1. **渲染架构**：继续原生静态多页、采用静态站点生成器，还是使用支持静态输出的组件框架？选择需兼顾 SEO、无 JavaScript可读、维护成本和托管环境。
2. **内容模型**：角色资料、技能倍率、来源、版本、玩法建议、媒体授权如何 schema 化；如何表达“待确认”、版本差异和多来源关系？
3. **内容存储与编辑**：Markdown/MDX、JSON/YAML、轻量 CMS 或其他方式；内容编辑是否需要非工程人员参与？
4. **路由与迁移**：专题单页 + 锚点和独立详情页如何划分；现有 `/HomePage/...`、`/About/...` URL 保留、跳转或归档策略是什么？
5. **组件边界**：页头、来源标签、技能折叠、构筑卡、队伍卡、剧透控制、画廊如何复用，并避免无障碍逻辑重复实现？
6. **版本治理**：游戏版本更新时如何标记受影响内容、触发复核、阻止过期建议继续显示为当前结论？
7. **来源追踪**：内容字段到来源记录的关联粒度、失效链接处置、核验历史与编辑责任如何保存？
8. **素材管线**：现有图片如何生成 AVIF/WebP、多尺寸和缩略图；如何在构建期阻止授权状态未知的素材进入发布包？
9. **字体与设计资源**：所选字体、纹理和图标的授权、子集化、自托管与回退策略是什么？
10. **交互降级**：标签、剧透、灯箱和当前章节在 SSR/静态 HTML、禁用 JavaScript、减少动画模式下分别如何工作？
11. **质量门禁**：HTML/内容 schema 校验、无障碍自动检查、链接检查、图片预算、Lighthouse 性能预算如何进入 CI？
12. **SEO 产物**：canonical、sitemap、robots、Open Graph、结构化数据和 404 由构建还是托管层生成？
13. **分析与隐私**：是否需要匿名统计；若需要，使用何种最小化方案、同意机制和数据保留策略？MVP 可决定不接入。
14. **部署边界**：目标静态托管环境、缓存、压缩、重定向和安全头支持情况是什么？本 PRD 不授权本轮执行外部发布。

## 19. 上线前仍需产品/内容确认的信息

- 万敌中文名、英文/罗马字名、称谓关系的官方写法。
- 属性、命途、稀有度、阵营、角色定位、首次可用版本等基础资料。
- 全部技能、行迹、星魂的名称、描述、倍率口径和适用版本。
- 光锥、遗器、词条、配队和操作循环的负责作者、依据与适用前提。
- 现有两段引语、“黄金蜜饼”说明和图书馆藏长文的准确出处、引用范围和版权处置。
- 现有 10 个图片/图标素材的来源、权利方、授权/合理使用判断和是否允许继续公开展示。
- 是否保留“黄金蜜饼”作为站名、彩蛋还是历史项目名；推荐让“万敌角色专题站”成为主品牌。
- “故事/时间线”可公开到何种剧情进度，以及默认剧透级别。
- 站主 QQ、邮箱、Bilibili 等联系方式是否继续公开。
- 目标托管环境、计划支持的浏览器版本、内容更新负责人和上线节奏。

## 20. 建议实施顺序

1. 先完成内容 schema、来源规则、素材授权台账和 URL/渲染架构决策。
2. 在不依赖完整倍率的情况下完成首屏、概览、导航、来源/声明与设计系统骨架。
3. 按“技能 → 行迹/星魂 → 机制循环 → 养成 → 配队”顺序录入并核验内容。
4. 完成移动端、键盘、读屏、减少动画和性能验收，再进入 MVP 发布评审。
5. MVP 稳定后审计并迁移故事长文，最后在授权充分时上线画廊和增强动效。

本 PRD 不构成对任何具体角色数据、技能倍率、剧情内容或素材授权的确认；所有未有可靠来源的内容均维持“待确认”。
